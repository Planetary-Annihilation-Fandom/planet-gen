# Ветки и выпуск версий planet-gen

## Назначение веток

Работа ведётся в [публичном репозитории planet-gen](https://github.com/Planetary-Annihilation-Fandom/planet-gen) через ветки, без pull request.

| Ветка | Содержимое |
|---|---|
| `main` | Опубликованное состояние проекта |
| `dev` | Готовые, но ещё не выпущенные изменения |
| Рабочая ветка `codex/<задача>` | Изменения одной задачи, созданные от актуального `dev` |

Готовую работу оставляй в рабочей ветке до явного разрешения пользователя на слияние. После разрешения вливай её в `dev` через `git merge --no-ff`; зависимости задачи должны уже находиться в `dev`. Отдельные `chore`- и релизные ветки не создаются.

Любое слияние, включая fast-forward и синхронизацию веток, требует явного разрешения пользователя. Просьба выполнить задачу такого разрешения не даёт; явная команда выпуска разрешает слияния по описанной ниже процедуре. В выпуск входит весь накопленный `dev`, неготовые задачи остаются в рабочих ветках.

## Номер версии

CLI, Rust-библиотека и Tauri-приложение выпускаются вместе с одной версией `x.y.z`. `x` повышается при существенном нарушении совместимости; `y` при изменении, требующем миграции сохранённых шаблонов или других данных; `z` при остальных изменениях. Номер повышается в релизном коммите непосредственно в `dev`, если пользователь не указал иной порядок.

Согласованное значение версии хранится в следующих файлах:

| Файл | Поле |
|---|---|
| `crates/planet-gen/Cargo.toml` | `package.version` библиотеки и CLI |
| `app/src-tauri/Cargo.toml` | `package.version` Tauri-приложения |
| `app/package.json` | `version` интерфейса |
| `app/src-tauri/tauri.conf.json` | `version` приложения |
| `Cargo.lock` | Версии пакетов `planet-gen` и `planet-gen-app` |
| `app/package-lock.json` | Корневая версия и `packages[""].version` |

Текущий исходный номер — `0.1.0`. Создание `dev` и настройка процесса сами по себе не являются новым выпуском и не меняют номер версии.

Описание готовящихся изменений ведётся в разделе «Не выпущено» файла [CHANGELOG.md](../CHANGELOG.md). При выпуске перенеси его содержание в раздел `X.Y.Z — YYYY-MM-DD`, указав фактическую дату выпуска. Результат работы и выполненную проверку также записывай в сообщении коммита; связанную issue закрывай после согласованного включения задачи в `dev`, отмечая, что изменения ещё не выпущены.

## Как выпустить версию

Выполняй процедуру только после явной команды пользователя выпустить изменения или обновить `main`. Все команды ниже выполняются из корня репозитория.

1. Выполни `git fetch origin --tags`, проверь чистоту рабочего дерева и состав `dev`. Если локальные и удалённые ветки разошлись, сначала разбери расхождение. В `dev` должны находиться все готовые задачи и их зависимости; во время подготовки выпуска новые задачи туда не вливаются.
2. Переключись на `dev`, повысь общую версию во всех перечисленных файлах и обнови `CHANGELOG.md`. Обнови lock-файлы штатными средствами Cargo и npm; убедись, что номер ещё не занят локальным или удалённым тегом. Создай релизный коммит с описанием изменений и совместимости.
3. Из каталога `app` выполни `npm ci` и `npm run tauri -- build --debug --no-bundle`. Запусти собранное приложение из `target/debug`, проверь изменённые сценарии и видимый результат. Убедись, что сборка работает без Vite. Автотесты и постоянные скрипты проверок в проект не добавляются.
4. Влей проверенный `dev` в `main` и поставь аннотированный тег на полученный коммит. Вместо `X.Y.Z` подставь подготовленный номер:

   ```powershell
   git switch main
   git merge --no-ff dev -m "release: planet-gen X.Y.Z"
   git tag -a vX.Y.Z -m "planet-gen X.Y.Z: изменения и совместимость"
   ```

   Если при слиянии изменилось проверенное содержимое, повтори затронутые проверки до отправки.
5. Синхронизируй `dev` с релизным коммитом и отправь обе ветки и конкретный тег одним атомарным push:

   ```powershell
   git switch dev
   git merge --ff-only main
   git push --atomic origin main dev refs/tags/vX.Y.Z
   ```

   После выпуска `main` и `dev` указывают на один коммит, тег `vX.Y.Z` отмечает этот коммит. Проверь удалённые ветки и тег; новые рабочие ветки снова создавай от `dev`.

## Как откатить изменение

Подготовь `git revert` в рабочей ветке от `dev`, без переписывания истории, и после разрешения пользователя влей результат в `dev`. Для уже опубликованных изменений проведи новый выпуск с повышением версии и новой датой; существующие теги не перемещай. Если в `dev` накоплены другие задачи, сначала согласуй состав выпуска: обычная процедура публикует весь `dev`.
